以下の手順で進めてください。

### 1. DDDベストプラクティスの調査

まずDDD（ドメイン駆動設計）のベストプラクティスをWeb検索や一次情報（Eric Evans / Vaughn Vernonの文献、公式的な解説記事など）で調査して理解してください。少なくとも以下の観点を押さえてください。

- ユビキタス言語（コード上の命名がドメインの言葉と一致しているか）
- 境界づけられたコンテキストとコンテキスト間の関係
- エンティティ / 値オブジェクトの使い分けと不変条件の保護
- 集約の設計（トランザクション整合性の境界、集約ルート経由のアクセス）
- ドメインサービス / アプリケーションサービスの責務分離
- リポジトリの抽象化とドメイン層のインフラ非依存（依存の方向）
- ドメインロジックの漏出（貧血ドメインモデル、サービス層への流出）

### 2. アプリケーションのドメインモデリングの理解

次に、このアプリケーションの実装を確認し、ドメインモデリングを理解してください。

- レイヤー構成・パッケージ構成から、ドメイン層がどこにあるかを特定する
- エンティティ・値オブジェクト・集約・リポジトリ・サービスに相当する実装を洗い出す
- ドメインモデル間の関係と、各モデルが守ろうとしている不変条件を読み取る

### 3. 敵対的検証

その上で、ステップ1のベストプラクティスに照らして違反をしていないか「敵対的検証」を行ってください。

ルール:
1. 実装を擁護しない。違反の可能性がある箇所を積極的に探しに行く
2. 「良い点」は書かない。違反または違反の疑いのある箇所だけを挙げる
3. 指摘は必ず実装上の根拠（ファイルパス・該当箇所）とともに示す
4. 確信の持てない指摘は無理に出さない。偽陽性は信頼を損なう

出力形式（指摘ごとに必ずこの4項目を付ける）:
- 指摘: どのDDD原則に違反している可能性があるか（一言で）
- 深刻度: 高（モデルの整合性が壊れる）/ 中（修正が必要）/ 低（条件つきで許容）
- 根拠: 該当する実装箇所（ファイルパス:行）と、違反と判断した理由
- 影響: 放置した場合にドメインモデルへ及ぶ影響
