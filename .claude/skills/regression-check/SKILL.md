実装によってデグレ（既存機能の退行）が起きていないか敵対的検証を行ってください。

**このアプリケーションでデグレを起こすと医療機関に甚大な被害（診療業務の停止、患者情報の誤り等）を及ぼすことを念頭において進めてください。** 「おそらく大丈夫」ではなく「デグレしていないと言い切れるか」を基準に判断してください。

以下の手順で進めてください。

### 1. 変更内容の把握

まず今回の実装による変更を正確に把握してください。

- `git diff` / `git log` で変更されたファイル・関数・設定を洗い出す
- 各変更が「何を変えたか」だけでなく「変更前はどう動いていたか」を必ず確認する

### 2. 既存挙動への影響調査

変更箇所が既存の挙動に与える影響を調査してください。

- 変更された関数・クラス・設定の呼び出し元・利用箇所をすべて洗い出す
- 共有されているデータ構造・DBスキーマ・API入出力の形式に変更がないか確認する
- 変更箇所を経由する既存のユースケースを特定し、変更前と同じ結果になるか追跡する

### 3. 敵対的検証

その上で、デグレが起きていないか「敵対的検証」を行ってください。少なくとも以下の観点で退行を積極的に探しに行ってください。

- 挙動の変化: 既存の入力に対して、変更前と異なる出力・副作用が発生するパスはないか
- 暗黙の契約: 呼び出し元が依存していた戻り値・例外・順序・デフォルト値・null許容が変わっていないか
- データ互換性: 既存データ（DBレコード、保存済みファイル、進行中のセッション）が新実装で正しく処理されるか
- 境界・異常系: 変更前は処理できていた境界値・異常入力が、変更後に失敗するようになっていないか
- 非機能: 性能劣化、トランザクション境界・ロック範囲の変化、タイムアウト挙動の変化がないか

ルール:
1. 実装を擁護しない。退行の可能性がある箇所を積極的に探しに行く
2. 「良い点」は書かない。デグレまたはデグレの疑いのある箇所だけを挙げる
3. 指摘は必ず根拠（変更前後の該当箇所 ファイルパス:行）とともに示す
4. 確信の持てない指摘は無理に出さない。偽陽性は信頼を損なう。ただし医療機関への影響が大きい箇所は、疑いの段階でも「未検証」と明記した上で挙げる

出力形式（指摘ごとに必ずこの4項目を付ける）:
- 指摘: どのような退行が起きる可能性があるか（一言で）
- 深刻度: 高（医療業務・患者データに影響）/ 中（機能退行）/ 低（限定的な影響）
- 根拠: 変更前後の該当箇所（ファイルパス:行）と、退行と判断した理由
- 再現条件: どの入力・状態・操作でデグレが顕在化するか
